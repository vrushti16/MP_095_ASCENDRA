============================================================
DIFFICULTY SYSTEM & FAIRNESS RULES
============================================================

Difficulty levels MUST progress through:

1 = BEGINNER
2 = NOVICE
3 = SKILLED
4 = EXPERT
5 = MASTER
6 = LEGEND

Difficulty MUST affect actual cognitive reasoning complexity and interaction depth.
Do NOT make higher difficulty simply mean more text, random clutter, or faster timers.

DIFFICULTY LEVEL SPECIFICATIONS:

1. BEGINNER (Level 1):
   - Single primary mechanism
   - Simple, direct reasoning
   - Obvious, clear clues
   - Small environment, 1-3 interactive objects
   - Direct cause and effect (e.g., align 3 number dials into simple ascending order).

2. NOVICE (Level 2):
   - Single main mechanism with 2 related clues
   - Slightly indirect solution requiring small exploration
   - 3-4 interactive elements.

3. SKILLED (Level 3):
   - Multiple interacting objects (3-5)
   - Two-step reasoning (e.g., discover code from a wall mural, then apply it to dial positions)
   - Meaningful object relationships and indirect environmental hints.

4. EXPERT (Level 4):
   - Multiple connected mechanisms (2 stages)
   - Multi-stage reasoning with distributed clues across 2-3 clue areas
   - Subtle environmental hints requiring deduction and pattern matching.

5. MASTER (Level 5):
   - Multi-stage connected puzzle (2-3 stages)
   - Advanced reasoning requiring synthesis of information from different sources (journal + mural + statue)
   - Several interacting mechanisms with state dependencies.

6. LEGEND (Level 6):
   - Major multi-stage challenge (3+ stages)
   - Interconnected mechanisms, hidden symbol relationships, and deep environmental exploration
   - Meaningful consequences for incorrect actions (mechanism recoil, reset of sub-stage)
   - High cognitive complexity that feels like a flagship adventure dungeon puzzle.

FAIRNESS RULE:
- Difficult does NOT mean impossible or unfair.
- Every puzzle MUST contain all necessary information for a purely logical solution within the game environment.
- NO puzzle may require:
  * blind guessing
  * brute-force trial-and-error as the primary solution
  * information external to the game world or unstated assumptions
  * domain knowledge outside the allowed category
  * unprovided or unsupported assets
  * unexplained or hidden mechanics

============================================================
PUZZLE STATE MODEL & STATE OWNERSHIP
============================================================

To enable Unity to manage real-time state transitions and allow authoritative server validation, the JSON defines a structured "puzzle_state" model.

CRITICAL STATE OWNERSHIP RULES:
1. The AI MUST generate `initial_state` and `target_state`.
2. The AI MUST NOT treat `current_state` as authoritative gameplay state:
   - The API cannot know the player's live physical interaction state during runtime.
   - In the initial JSON response, `current_state` (if included for schema compatibility) MUST simply be initialized equal to `initial_state`.
3. Unity OWNS and dynamically updates `current_state` during runtime gameplay:
   - When the player interacts (e.g. rotates object_01 from 0 -> 1 -> 2 -> 3), Unity updates its local `current_state`.
4. The server-side validator compares the authoritative runtime `current_state` submitted by Unity against `target_state` / `required_state`.

JSON FIELD SPECIFICATION:
"puzzle_state": {
    "initial_state": {
        "object_01": 0
    },
    "current_state": {
        "object_01": 0
    },
    "target_state": {
        "object_01": 3
    },
    "reset_on_failure": true
}

The state objects map interactable object IDs to their required numerical, rotational, string, or boolean values.

============================================================
MACHINE-READABLE VALIDATION, SINGLE SOURCE OF TRUTH & ANTI-CHEAT
============================================================

Validation MUST be state-based, machine-readable, and verified authoritatively on the server.
Do NOT rely on free-form text comparison or client-side trust.

SINGLE SOURCE OF TRUTH RULE:
- `validation.required_state` is the SINGLE AUTHORITATIVE VALIDATION TARGET.
- To prevent contradiction, `puzzle_logic.solution_state` and `puzzle_state.target_state` must exactly match `validation.required_state`.
- The server validator uses `validation.required_state` as the definitive ground truth to compare against the client's submitted runtime mechanism state.

JSON FIELD SPECIFICATION:
"validation": {
    "type": "state_based",
    "validation_rule": "rule_identifier_string",
    "required_state": {
        "object_id_1": target_value_1,
        "object_id_2": target_value_2
    },
    "allow_retry": true
}

The authoritative server validator compares the physical mechanism state submitted by the client (e.g., ring_01=3, ring_02=7, lever_01=1) against `required_state`.
If the submitted state matches `required_state`, the server signs the completion token and awards progress.

============================================================
MOST IMPORTANT DESIGN PRINCIPLE
============================================================

ASCENDRA IS NOT A QUIZ GAME.

The player should never feel:
"I am answering an exam question."

The player should feel:
"I discovered something in this world."
"I need to figure out how this mechanism works."
"I need to explore this room."
"I need to understand these clues."
"I need to manipulate these objects."
"I solved the mechanism."
"I unlocked the next part of my adventure."

The educational concept MUST be hidden INSIDE the gameplay mechanic.
LEARNING + EXPLORATION + INTERACTION + DISCOVERY must work together as one seamless game experience.
============================================================
